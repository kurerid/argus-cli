# Argus — техническое задание первой версии

Дата: 29 октября 2026 года. Статус: спецификация MVP для последовательной разработки.

## 1. Цель и границы

Argus — CLI-инструмент, который анализирует изменения между вершинами двух веток Git в нескольких репозиториях одного продукта и формирует один автономный HTML-отчёт о релизе.

Первый пользователь — автор проекта. Архитектура и установка должны позволять впоследствии распространять Argus как open-source инструмент для других продуктов.

Основной проверочный сценарий MVP: совместный анализ фронтенда и API. Для каждого репозитория пользователь задаёт исходную и целевую ветки, например `master` и `release/1.2.3`.

Результат должен помогать:

- понять изменения пользовательских сценариев;
- увидеть технические изменения, исправления и риски совместимости;
- выбрать проверки перед выкладкой;
- сформулировать проверяемые гипотезы о бизнес-эффектах.

Argus не принимает решение о выкладке. Отчёт по исходникам не доказывает, что приложение работает в браузере или на сервере.

### 1.1. В MVP входит

- Go CLI для локального запуска и Jenkins;
- OpenAI-совместимый API с настраиваемыми адресом, моделью и секретом;
- локальный кеш репозиториев с получением изменений через Git/SSH;
- сравнение зафиксированных SHA вершин двух удалённых веток каждого репозитория;
- доступ к истории, полным файлам обеих версий, тестам и документации;
- обязательное подтверждённое описание продукта;
- самостоятельная подготовка и обновление описания продукта с подтверждением человеком;
- исключения файлов по правилам, аналогичным `.gitignore`;
- настраиваемые пороги размера изменений и автоматический анализ частями;
- общий необязательный лимит токенов;
- частичные отчёты, диагностика и три кода завершения;
- автономный HTML с вкладками «Продукт», «Разработка», «QA» и настраиваемым языком.

### 1.2. За пределами MVP

- выполнение браузерных и API-тестов, взаимодействие с production;
- заключение «можно выкатывать» и автоматическое разрешение/блокирование релиза по найденным рискам;
- подключение через подписки Codex или Claude;
- сбор фактических бизнес-метрик из аналитики;
- серверное приложение Argus, учётные записи пользователей и веб-панель;
- отправка отчётов в мессенджеры, комментарии PR/MR и другие внешние системы;
- автоматическое изменение исходников, коммиты, push и создание релизных веток.

Будущий модуль браузерных тестов: отдельный исполнитель TypeScript + Playwright под управлением Go-ядра. Его реализация и Node.js не требуются для MVP.

## 3. Основные понятия и правила

### 3.1. Проект и репозитории

Проект Argus объединяет описание продукта, настройки и один или несколько именованных репозиториев. MVP обязательно проверяется на двух репозиториях: `frontend` и `api`; эти имена не должны быть зашиты в алгоритмы.

Пользователь самостоятельно создаёт аккаунт на Git-хостинге, выдаёт права чтения, добавляет публичный SSH-ключ. Argus получает URL репозиториев и путь к приватному ключу либо использует настроенный SSH-agent. Содержимое ключа не хранится в конфигурации и отчётах.

При первом обращении Argus клонирует репозиторий в собственный кеш, затем выполняет `fetch`. Рабочая ветка и `pull` для анализа не требуются. Кеш может быть bare-репозиторием.

После обновления исходников фиксируются SHA исходной и целевой веток. Последующие изменения веток не меняют текущий анализ. Между независимыми репозиториями не предполагается атомарного снимка: сохраняются SHA и время фиксации каждого.

Сравниваются конечные деревья исходного и целевого SHA, а не diff от merge-base. Если в исходной ветке появились отдельные изменения, их отсутствие в целевой версии также является частью сравнения.

Название `master` само по себе не доказывает, что именно этот SHA развёрнут в production. Отчёт описывает выбранные состояния Git.

### 3.2. Подтверждение описания продукта

До анализа релиза необходимо подтверждённое описание: назначение, роли, ключевые сценарии, бизнес-цели, назначение репозиториев и известные неизвестные.

Описание может написать человек или подготовить Argus по исходникам. Argus не выдаёт выведенные из кода бизнес-цели за установленные факты.

Подтверждение — отдельное явное действие пользователя. Argus сохраняет хеш подтверждённого содержимого и привязку к набору репозиториев. Редактирование файла или изменение набора репозиториев требует нового подтверждения. Отсутствующее или неподтверждённое описание блокирует анализ релиза и в интерактивном режиме, и в Jenkins.

Обновление описания запускается отдельно, не перезаписывает подтверждённый файл без явного действия и требует подтверждения новой версии. Анализ релиза лишь сообщает о найденных противоречиях описанию.

### 3.3. Исключения и размер изменений

В проекте используется `.argusignore` с шаблонами файлов, директорий и расширений. Поддерживаются комментарии, пустые строки, шаблоны директорий, `*`, `**`, привязка к корню и отрицания `!` с документированной семантикой `.gitignore`.

Правила применяются относительно корня каждого репозитория одинаково при сканировании diff и при дополнительном чтении файлов моделью. Исключённое содержимое не передаётся модели. При переименовании проверяются старый и новый пути; чтение каждой стороны разрешается только для не исключённого пути.

Отдельно считаются:

1. Добавленные строки в не исключённых текстовых файлах.
2. Удалённые строки в не исключённых текстовых файлах.
3. Количество не исключённых изменённых файлов.

Для многорепозиторного запуска пороги применяются к суммарным значениям; статистика каждого репозитория также сохраняется. При строгом превышении любого порога включается анализ частями. Равенство порогу не считается превышением.

Ниже порогов анализ также делится, если иначе запрос не помещается в контекст выбранной модели. Порог не является разрешением превысить технический предел модели.

Переименованный файл учитывается один раз; чистое переименование может иметь ноль добавленных/удалённых строк. Бинарные файлы учитываются в количестве файлов, но не имеют выдуманного числа строк. Их изменения обозначаются как изменения, содержимое которых не разобрано. Сгенерированные файлы исключаются явными правилами, а не скрытыми эвристиками.

Отчёт показывает количество исключённых файлов. Пропущенные из-за ошибки или бюджета файлы учитываются отдельно от намеренно исключённых.

### 3.4. Полнота и результат запуска

| Результат  | Код | Значение                                                                                                |
| ---------- | --- | ------------------------------------------------------------------------------------------------------- |
| `complete` | `0` | Весь запланированный анализ в заявленных границах завершён, HTML сохранён                               |
| `failed`   | `1` | Пригодный отчёт не создан: неверная конфигурация, неподтверждённый контекст или другая фатальная ошибка |
| `partial`  | `2` | Пригодный HTML сохранён, но часть анализа не завершена                                                  |

Наличие рисков, исправлений или неясных изменений не меняет код полного анализа. «Полный» означает полноту обработки выбранного объёма, а не отсутствие багов и не полноту автоматического тестирования.

Если ветки одинаковы, формируется полный отчёт «Изменений нет» без выдуманных выводов и без обращения к модели для анализа релиза.

При недоступности одного репозитория по умолчанию анализ остальных продолжается. Настройка позволяет остановиться. Если анализ остановлен, но полезный частичный HTML создан, код — `2`; если пригодный отчёт создать не удалось — `1`. Если недоступны все репозитории, создаётся диагностика, результат — `failed`.

Неясное изменение — изученное изменение, по которому недостаточно оснований для уверенного объяснения. Оно само по себе не делает отчёт частичным.

### 3.5. Лимит токенов

Необязательный лимит относится ко всему одному запуску команды: все репозитории, все запросы, повторные попытки, подготовка итоговой структуры, входные и выходные токены. Генерация описания продукта является отдельным запуском со своим лимитом.

Argus резервирует бюджет на завершение сводки. HTML собирается программно и не требует дополнительного запроса к модели. В отчёте разделяются фактический расход, сообщённый API, и оценка Argus.

Перед запросом оценивается полный вход, резервируется максимальный выход. Если запрос не помещается в оставшийся бюджет, он не отправляется. Полученный расход сверяется с резервом. Неучтённые повторы SDK не допускаются.

OpenAI-совместимые провайдеры могут различаться в учёте токенов и поддержке ограничений. Нельзя обещать точный финансовый потолок у любого провайдера. При включённом лимите и невозможности надёжно ограничить/оценить очередной запрос Argus завершает анализ частичным отчётом с объяснением, а не молча игнорирует лимит.

Без общего лимита обработка продолжается до завершения. Сетевые таймауты, ограниченное число повторов и защита от бесконечного цикла инструментария действуют независимо от бюджета.

## 4. Интерфейс пользователя

Названия команд и файлов ниже — проектное решение этой спецификации, ранее обсуждалась их функция. Изменение этих названий не должно менять согласованное поведение.

### 4.1. Команды

| Команда                                               | Назначение                                                              |
| ----------------------------------------------------- | ----------------------------------------------------------------------- |
| `argus init --project <dir>`                          | Создать папку проекта и конфигурацию по умолчанию                       |
| `argus config show --project <dir>`                   | Показать эффективную конфигурацию без секретов                          |
| `argus config set <key> <value> --project <dir>`      | Изменить поддерживаемый параметр с валидацией                           |
| `argus doctor --project <dir>`                        | Проверить настройки, Git/SSH, доступ к репозиториям и API               |
| `argus context generate --project <dir>`              | Изучить репозитории и подготовить черновик описания                     |
| `argus context confirm --project <dir> --file <path>` | Явно подтвердить проверенный человеком файл                             |
| `argus context update --project <dir>`                | Подготовить новую версию описания, сохранив предыдущую                  |
| `argus report --project <dir>`                        | Обновить исходники, зафиксировать SHA, провести анализ и сохранить HTML |

CLI поддерживает `--help`, `--version`, неинтерактивный режим и переопределения настроек через документированные флаги. В частности, ветки задаются отдельно для каждого репозитория: повторяемые `--base <repo>=<branch>` и `--head <repo>=<branch>`.

Приоритет параметров: встроенные значения → файл проекта → поддерживаемые переменные окружения → явные флаги. `config set` меняет файл проекта; флаг влияет только на текущий запуск.

Каждый рабочий запуск показывает безопасную сводку эффективных настроек и подсказку «Вы всегда можете изменить настройки командой … или флагом …». Для Jenkins вывод не требует TTY. Диагностика и прогресс идут в stderr; итоговое сообщение сообщает код результата и абсолютный путь к HTML, если он создан.

### 4.2. Структура папки проекта

```text
<project>/
  argus.yaml
  .argusignore
  product.md
  product.approval.json
  drafts/
  reports/
    <run-id>/
      report.html
      report.json
      run.json
      analysis.json
```

Кеш репозиториев хранится отдельно, в настраиваемой директории кеша Argus. В проекте не должно автоматически появляться содержимое приватного SSH-ключа или API-ключа. Файлы подтверждения переносимы между рабочей машиной и Jenkins; локальные кеши и блокировки — нет.

`run-id` уникален. Повторный запуск не перезаписывает прежний отчёт. Артефакты содержат версии схемы, Argus, хеши контекста/эффективных настроек без секретов, SHA, время, статистику и причины неполноты.

### 4.3. Стартовые значения

Следующие числа — стартовые инженерные значения, а не доказанная граница сложности. Они должны быть настраиваемыми и пересмотрены после приёмки реального релиза.

| Параметр                                  | Стартовое значение                         |
| ----------------------------------------- | ------------------------------------------ |
| Язык                                      | `ru`                                       |
| Добавленные строки                        | `1000`                                     |
| Удалённые строки                          | `1000`                                     |
| Изменённые файлы                          | `30`                                       |
| Общий лимит токенов                       | Не задан                                   |
| Ошибка репозитория                        | Продолжить остальные                       |
| Вкладка при открытии                      | «Продукт»                                  |
| Повторы временно неуспешного HTTP-запроса | Не более `2` повторов после первой попытки |
| Таймаут одной HTTP-попытки                | `120` секунд                               |

URL репозиториев, ветки, модель и адрес API не угадываются. Инициализация создаёт шаблон; до заполнения обязательных параметров анализ не начинается. API-ключ передаётся через окружение, в том числе Jenkins Credentials. Значения контекстного окна и предела ответа задаются в профиле модели; неизвестная модель не получает произвольные «универсальные» значения.

## 5. Требования к отчёту

Общая часть показывает продукт, дату, сравниваемые ветки и SHA всех репозиториев, полноту, причины частичности, статистику diff и число исключённых файлов. Для частичного отчёта предупреждение видно сразу и на каждой вкладке.

### «Продукт»

- Изменения пользовательских сценариев, сформулированные понятным языком.
- Ожидаемые бизнес-эффекты и предлагаемые метрики проверки, только если есть связь с изменениями.
- Один общий текст перед эффектами: «Ожидаемые бизнес-эффекты — гипотезы. Их необходимо проверить измерениями после релиза».
- Нет повторяющегося поля «Статус» у каждого эффекта.
- Нет придуманных чисел конверсии, выручки, экономии времени или достигнутых улучшений.

### «Разработка»

- Техническое описание изменений и исправлений.
- Риски совместимости, изменения API, миграций, настроек и зависимостей, если они обнаружены.
- «Неясные изменения»: что изменилось и чего не удалось установить.
- Противоречия подтверждённому описанию продукта, если они найдены.

### «QA»

- Конкретный список «Что проверить», связанный с изменёнными сценариями и рисками.
- Список не разрастается в пошаговые тест-кейсы.
- Общее пояснение, что проверки рекомендованы и не выполнялись Argus.

У каждого существенного вывода есть список затронутых файлов с идентификатором репозитория. Код, полные промпты и содержимое секретов в HTML не включаются. Нельзя утверждать, что баг исправлен, если оснований достаточно только для формулировки «изменена обработка …».

HTML открывается напрямую как локальный файл, без HTTP-сервера и сети. Все стили, вкладки и другие ресурсы встроены. Внешние шрифты, CDN, аналитика и внешние запросы отсутствуют. Переключение вкладок доступно с клавиатуры; длинные имена файлов и узкое окно не ломают чтение.

## 6. Порядок разработки

Задачи выполняются последовательно. Зависимости указывают минимальные предварительные условия, но порядок ниже менять без причины не следует.

Задача закрывается, когда выполнены **все** её критерии и сохранено указанное подтверждение. При недоступности внешнего сервиса критерий остаётся открытым. Мок-тесты не заменяют проверку настоящего SSH, настоящего API модели, Jenkins или знакомого релиза.

### ARG-014. Собрать сквозную команду report

**Зависимости:** ARG-013.

**Работа:** связать настройки, проверку подтверждения, обновление Git, снимки, diff, план, модель, сводку, сохранение JSON/HTML и итоговый код.

**Критерии приёмки:**

- [ ] Одной командой после первоначальной настройки создаётся отчёт по двум настоящим репозиториям и выбранным веткам.
- [ ] До анализа показаны эффективные настройки и подсказка изменения; после — результат и путь к HTML.
- [ ] `0` выдаётся только после успешного сохранения полного HTML; `2` — после сохранения пригодного частичного; иначе `1`.
- [ ] По умолчанию недоступность одного репозитория не мешает анализу другого; настройка остановки действительно меняет поведение.
- [ ] Исчерпание бюджета сохраняет уже полученные выводы и явную причину частичности, без следующих запросов анализа.
- [ ] Одинаковые состояния дают отчёт «Изменений нет» и не расходуют токены анализа.
- [ ] Сохранены report/run/analysis JSON с совпадающими SHA и статистикой; повторный запуск не перезаписывает предыдущий.
- [ ] Полный отчёт с обнаруженным риском возвращает `0`, а не принимает решение о выкладке вместо человека.

**Подтверждение:** записанные команды и артефакты полного, частичного, неуспешного и пустого запусков.

### ARG-015. Проверить отказы, прерывание и сохранность результатов

**Зависимости:** ARG-014.

**Работа:** завершить обработку ошибок, сохранение при отмене, защиту кешей и согласованность артефактов. Автоматическое продолжение прерванного запуска не входит в обязательный MVP.

**Критерии приёмки:**

- [ ] Проверены таймаут, rate limit, неправильный JSON, постоянная ошибка API и отказ Git; нет бесконечных повторов.
- [ ] При управляемом прерывании Argus отменяет новые запросы и пытается сохранить доступный частичный HTML; поведение и код документированы.
- [ ] При невозможности записи/нехватке места не объявляется успешное сохранение; предыдущие отчёты целы.
- [ ] Параллельные запуски не повреждают кеш, снимки, подтверждение контекста и отчёты друг друга.
- [ ] Ошибка финальной сводки не уничтожает результаты уже завершённых групп.
- [ ] Ошибка конфигурации не запускает платные запросы; неверный контекст не обходится флагом неинтерактивности.
- [ ] Логи и артефакты проверены на отсутствие SSH/API-секретов; диагностическое сообщение объясняет действие для исправления.

**Подтверждение:** матрица отказов «условие → ожидаемый результат → фактический результат → артефакт».

### ARG-016. Подготовить установку и документацию

**Зависимости:** ARG-015.

**Работа:** сборка для Linux/macOS/Windows, инструкция первого запуска, конфигурация, исключения, профили моделей, коды результатов. Первый обязательный целевой запуск — Linux/Jenkins; остальные платформы нельзя объявлять проверенными только по успешной кросс-компиляции.

**Критерии приёмки:**

- [ ] Подготовлены версионируемые бинарные сборки с контрольными суммами и указанными зависимостями Git/SSH.
- [ ] Есть пошаговый путь: аккаунт/ключ → init → настройки → doctor → описание → подтверждение → report.
- [ ] Описаны все настройки/флаги, стартовые значения, приоритеты и примеры `.argusignore`.
- [ ] Объяснены Git SHA, границы полноты, гипотезы, токены, частичные отчёты и три кода завершения.
- [ ] `doctor` проверяет реальные зависимости/доступы, не меняет продуктовый код и сообщает, если проверка API расходует токены.
- [ ] Опубликована матрица фактически проверенных ОС и провайдеров; непроверенные сочетания обозначены явно.
- [ ] Инструкция установки и первого запуска воспроизведена в чистой Linux-среде без Go, Node.js и БД на стороне пользователя.

**Подтверждение:** артефакты сборки и протокол установки. Выбор open-source лицензии — отдельное решение владельца до публичного распространения, а не предположение реализации.

### ARG-017. Подключить и проверить Jenkins

**Зависимости:** ARG-016.

**Работа:** пример Jenkinsfile и реальный запуск на выбранном пользователем этапе пайплайна. SSH/API-секреты поступают через Jenkins Credentials; браузерный сервер для отчёта не требуется.

**Критерии приёмки:**

- [ ] Jenkins без TTY использует подтверждённое описание и получает обе пары веток из параметров/конфигурации.
- [ ] Выполняется настоящий SSH clone/fetch и запрос к настоящей модели, создаётся совместный HTML.
- [ ] Секреты не выводятся; выбор ключа/host keys документирован без отключения проверки сервера.
- [ ] HTML и диагностические JSON сохраняются как артефакты и при коде `2`; при `1` сохраняется доступная диагностика.
- [ ] Пример различает три кода и показывает настраиваемую реакцию Jenkins; риски отчёта не подменяют решение человека.
- [ ] Повторный запуск использует доступный кеш либо корректно создаёт новый на другом агенте; подтверждение контекста переносимо.
- [ ] Скачанный HTML открывается автономно; установка Jenkins HTML Publisher не является обязательной.

**Подтверждение:** ссылка/идентификатор настоящей сборки, безопасный лог и скачанный отчёт. Один пример Jenkinsfile без запуска не закрывает задачу.

### ARG-018. Провести приёмку на знакомом реальном релизе

**Зависимости:** ARG-017.

**Работа:** пользователь предоставляет репозитории и ветки фронтенда/API. До просмотра результата составляется контрольный список известных существенных изменений, исправлений, рисков и необходимых QA-проверок. Затем выполняется полный прогон и разбираются расхождения.

**Критерии приёмки:**

- [ ] Зафиксированы четыре SHA, конфигурация, модель, подтверждённый контекст, расход/оценка токенов и артефакты запуска.
- [ ] Все заранее перечисленные существенные изменения отражены либо явно обозначены как неясные с достаточным объяснением; необъяснённые пропуски исправлены и перепроверены.
- [ ] Каждое существенное утверждение проверено по коду; нет неподтверждённых заявлений об исправленных багах или выполненных проверках.
- [ ] Бизнес-гипотезы относятся к фактическим изменениям сценариев и снабжены подходящими метриками проверки; достигнутые результаты не выдуманы.
- [ ] Пользователь подтверждает, что список QA помогает выбрать проверки конкретного релиза.
- [ ] Прогон с намеренно малым бюджетом создаёт честный частичный отчёт; прогон с недоступным репозиторием подтверждает оба режима настройки.
- [ ] Проверены вкладки, язык, автономность и читаемость реального HTML; пороги по умолчанию пересмотрены по фактическому объёму или оставлены с объяснением.
- [ ] Каждое расхождение имеет статус «исправлено и перепроверено» либо явно принятое ограничение; незакрытые существенные ошибки не маскируются статусом готовности.

**Подтверждение:** матрица приёмки с конкретными ожидаемыми находками, фактическими выводами и ссылками на артефакты. Моки и синтетические примеры не заменяют этот этап.

## 7. Общее правило завершения MVP

MVP готов после закрытия ARG-001—ARG-018, включая настоящий SSH, настоящий API модели, Jenkins и подтверждённое пользователем качество отчёта на реальном релизе.

Для каждой задачи в журнале разработки указываются:

- выполненные критерии;
- способ и результат проверки;
- артефакты/команды воспроизведения;
- оставшиеся ограничения и непроверенные условия.

Готовность отчётного MVP не означает готовность будущего тестирующего агента, снижение количества production-багов или отказ от ручного тестирования. Эти цели потребуют отдельного ТЗ и проверки модуля тестирования до и после выкладки.
